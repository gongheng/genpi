# PRD：把模糊想法变成可开发的需求文档

只读不改代码——产出 prd.md，经人工批准（GATE_PRD）后即为交付物。

## prd.md 结构

1. **背景与目标**：为什么做/解决谁的什么问题/成功指标（可量化）
2. **用户故事**：作为<角色>，我想<动作>，以便<价值>；覆盖主流程与边界角色
3. **验收标准**：可测场景（GIVEN/WHEN/THEN）；每条可独立验证，避免"体验良好"类不可测表述
4. **非目标**：明确不做什么（≤5 条），防范围蔓延
5. **优先级与分期**：P0 必须/P1 应该/P2 可以；第一期边界清晰

## 写作纪律

- 每个术语首次出现给出定义，全文同一词同一义
- 需求有歧义时列出可选解释并给出推荐项，标"待确认"而非自行拍板
- 验收标准覆盖错误路径（输入非法/服务不可用/权限不足），不只写 happy path
- 不写实现方案（技术选型/接口设计属于下游 design.md，本文档面向"做什么"而非"怎么做"）

## 检验

- 开发者读后能在不追问的情况下开工
- 每条验收标准都能想出对应的验证方法
- 删掉任何一节，文档仍不自相矛盾（节间无隐含依赖）
